# 升级路线

本文记录 myMemory 当前能力边界，以及三条可选的升级路线。每条路线都写清了**触发条件**与**代价**，
便于在不影响既有功能的前提下逐步替换 —— 转写与生成都通过 Provider 接口注入，替换实现不需要改动业务代码与页面结构。

## 一、当前能力

| 能力 | 实现方式 | 是否依赖网络 | 局限 |
|---|---|---|---|
| 语音转写 | 浏览器内置语音识别（Web Speech API） | 是 | 只接受实时麦克风，不能转已录好的音频；国内 Chrome 可能因无法访问其识别服务而失败 |
| 转写备用 | 后端 `StubSpeechToTextProvider` | 否 | 返回占位文本，仅保证链路与错误码可验证 |
| 初稿生成 | 后端 `StubGenerationProvider`（规则引擎） | 否 | 只能去填充词、分段，写不出传记语感 |
| 数据存储 | 浏览器 IndexedDB | 否 | 换浏览器不共享 |
| 文档导出 | 后端拼装 OOXML | 否 | 无 |

两处实现都通过接口注入：

```csharp
builder.Services.AddSingleton<ISpeechToTextProvider, StubSpeechToTextProvider>();
builder.Services.AddSingleton<IGenerationProvider, StubGenerationProvider>();
```

替换时只需换掉这两行，`appsettings.json` 的 `Providers:*:Mode` 已预留切换位。

## 二、为什么停在这里

三条硬约束叠加的结果：

1. **分发形态**：目标是「解压双击即用、无需配置」，因此不能要求使用者安装运行时、模型或配置密钥。
2. **体积**：可用质量的中文语音模型至少 42MB，质量更好的在 90–230MB，会让分发包从 41MB 涨到 80–270MB。
3. **可分发的大模型**：能把口述整理成传记的模型至少 7B 级别，量化后 4GB 以上，无法随网页项目分发。

## 三、路线一：接入云端语音识别

**适用场景**：需要转写已录音频、需要更高准确率、使用者能自行申请密钥。

**为什么值得做**：当前方案最大的限制是「只能实时识别」，一旦录音结束就无法重跑；云端方案没有这个限制，
`POST /api/transcriptions` 可以恢复原有语义，转写失败也能真正重试。

**技术方案**：

| 环节 | 做法 |
|---|---|
| 接口 | 保留现有 `POST /api/transcriptions`（multipart），前端无需改动 |
| 实现 | 新增 `CloudSpeechToTextProvider`，用 `HttpClientFactory` 调用供应商 REST 接口 |
| 鉴权 | 密钥只在后端读取（`appsettings.json` 或用户配置文件），前端永远拿不到 |
| 超时与重试 | 复现既有错误码 `MYM_2001`（服务不可用）/`MYM_2002`（超时）/`MYM_2003`（结果为空） |
| 格式 | 需要把 webm/opus 转成供应商要求的采样率格式；若供应商支持直接上传，则跳过一次转码 |

**代价**：按量计费；录音离开本机，必须在界面明确告知；离线不可用。

**改动量估计**：新增一个 Provider（约 120 行）+ 配置项，业务层与前端零改动。

## 四、路线二：内置离线语音识别

**适用场景**：要求音频永不离开本机，或必须在无网络环境使用。

**候选方案**：

| 方案 | 体积 | 中文效果 | 运行位置 | 备注 |
|---|---|---|---|---|
| Vosk small-cn | 约 42MB | 中等 | 前端 WASM | 体积最小，流式识别，最适合「能内置」这一条 |
| sherpa-onnx（Paraformer / SenseVoice 小模型） | 90–230MB | 明显更好 | 前端 WASM 或后端原生 | 体积换质量，首次加载较慢 |
| whisper.cpp（tiny / base） | 75–142MB | 中文偏弱 | 后端原生 | 生态最好，但中文不是强项 |

**必须处理的技术点**：录音产物是 webm/opus，模型需要 16kHz 单声道 PCM，
浏览器内用 `AudioContext.decodeAudioData` 转一次即可，无需 ffmpeg。

**代价**：分发包体积翻倍以上；首次加载模型有明显等待；口音与方言识别率下降，需要准备「识别不准、请直接编辑」的兜底路径。

## 五、路线三：云端大模型润色

**适用场景**：需要真正的传记语感，而不是单纯的去噪与分段。

**为什么规则引擎不够**：规则引擎只能做减法（删填充词、断句），无法做结构重组（把碎片化的口语整理成有先后的叙述），
也无法按「童年—求学—工作」这类线索重排内容。

**关键约束**：提示词必须硬性规定「不得新增人物、时间、地点、事件」，输出后建议再做一次事实核对
（把输出中的人名、年份、地名与原文比对，出现原文没有的实体则标记为待人工确认）。

**代价**：需要密钥与费用；存在模型幻觉风险，需要上述核对环节。

## 六、密钥管理（使用者自带）

如果接入任何云端能力，密钥按以下方式处理：

| 环节 | 做法 |
|---|---|
| 入口 | 首次启动时在设置页填写，跳过也能正常使用本地能力 |
| 存储 | 使用 Windows DPAPI 加密后写入用户目录，不写进仓库、不随分发包走 |
| 使用 | 只由后端读取并调用外部服务，前端不接触 |
| 校验 | 提供「测试连接」按钮，返回可用 / 密钥无效 / 额度不足三类结果 |
| 清除 | 清空密钥后自动退回规则引擎，界面状态标签同步变化 |
| 声明 | 填密钥时明确提示：启用后录音或文本会发送给所选服务商 |

**绝不采用**：把项目方的密钥打包进分发包。分发件一旦被解压即可提取，等同于公开泄露，且额度会被他人消耗。

## 七、与原设计的差异

详细设计文档把语音转写定为「经自有后端代理调用外部识别服务」，`POST /api/transcriptions` 是唯一入口。
当前实现改成了浏览器内置识别，两者因此产生一处刻意保留的差异：

| 项 | 原设计 | 当前实现 |
|---|---|---|
| 转写入口 | `POST /api/transcriptions` | 录音时浏览器直接识别，不打后端 |
| 该接口的角色 | 主路径 | 备用路径（浏览器不支持或识别失败时才调用） |
| 密钥 | 后端持有 | 不需要 |
| 能否转写已录音频 | 能 | 不能 |

选择当前实现的理由：不需要密钥、不增加分发体积，能让识别立刻真实可用。
这处差异会在接入**路线一**后被消除 —— 届时 `POST /api/transcriptions` 恢复为主入口，
设计与实现重新一致。设计文档保持原样未改，以便对照当初的判断。

### 第二处差异：初稿整理

设计文档把这一步定为「AI 润色」：由大模型改写语句、调整结构与文风，产出有传记感的初稿。
当前实现是**规则引擎**，两者能力不在一个量级：

| 项 | 原设计（AI 润色） | 当前实现（规则引擎） |
|---|---|---|
| 做的事情 | 改写语句、组织段落、调整文风 | 去口语填充词、收敛标点、按段落排布 |
| 是否改写文字 | 是，会重写句子 | **否**，只在删除填充词与标点收敛时改动 |
| 事实风险 | 存在幻觉可能，需约束提示词 | 无，不新增任何内容 |
| 产出效果 | 有传记感的成稿 | 可读的整理稿，文风仍是本人原话 |
| 依赖 | 大模型 API 与密钥 | 无 |

选择当前实现的理由与转写一致：不需要密钥、可离线、零依赖，且**不会因为模型幻觉而偏离事实**。
代价也要说清楚：它做不到「润色」，交出的初稿更接近"整理后的原文"，用户仍需自己补写与调整文风。
这处差异会在接入**路线三**后被消除，届时规则引擎退化为无密钥时的兜底。

侧边栏与页面上的引擎标签会如实显示当前是哪一种（`规则引擎整理` / `AI 生成`），
不把整理稿说成润色稿。

## 八、路线选择建议

| 如果你更在意 | 建议先做 | 理由 |
|---|---|---|
| 尽快看到真实效果 | 路线一 | 改动最小，`POST /api/transcriptions` 语义完整恢复 |
| 音频绝不外传 | 路线二 | 唯一能满足隐私承诺的方案 |
| 初稿质量 | 路线三 | 规则引擎的天花板在「整理」，不在「写作」 |
| 分发包保持轻量 | 路线一 + 路线三 | 两者都不增加分发体积 |

三条路线互不冲突，可以先做路线一验证链路，再按需要补路线二或路线三。
