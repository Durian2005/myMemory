1. 文档说明

1.1 文档目的

本文档把《myMemory 口述记录生成传记系统 PRD（人工修改版）》转换为可执行的工程方案，用于在正式编码前固定技术方案的六大核心模块：技术栈选型、系统整体架构、项目模块划分、数据表结构、开发命名与目录规范、风险预案。

在此基础上，本文档进一步补充了数据保存位置、语音识别与 AI 润色的调用方式、接口清单、页面结构与原型、非功能指标、里程碑节奏与验收标准，作为开发阶段的唯一技术依据；后续如需调整，应同步更新本文档并记录变更原因。

1.2 适用范围

适用于网页微缩版的第一版实现（对应里程碑 M1 至 M4）。不适用于未来可能出现的云同步版本、机构版或多语言版本。

1.4 术语约定

  • 记录（Story）：一条传记记录，包含标题、最终正文和若干口述片段。
  • 片段（Segment）：一次录音或一次音频上传产生的口述素材，同一记录下可存在多段。
  • 原始转写文本：语音识别直接输出的文本，不允许被覆盖。
  • 润色文本：AI 在原始转写文本基础上整理生成的传记初稿。
  • 本地优先：用户数据默认保存在当前设备浏览器中，后端不持久化用户音频与文本。

2. 核心目标

2.1 产品目标

让不擅长打字的中老年用户，用“说”的方式完成人生经历的记录，并得到一份可阅读、可修改、可导出的传记初稿。

2.2 技术目标

  1. 用一条最小可运行闭环支撑完整业务：创建记录 → 录音 → 转写 → 润色 → 编辑 → 导出。
  2. 在语音识别或 AI 服务不可用时，产品仍可作为“本地录音 + 文本编辑 + 文档导出”工具独立运行。
  3. 用户数据默认保留在本地，密钥与外部调用集中在后端，前端不接触任何凭据。
  4. 核心逻辑可测试、可回放，异常路径不丢失用户已有内容。

2.3 成功标准

维度可度量标准
流程完整性用户从零开始可在 5 分钟内完成“新建记录 → 完成一段录音 → 得到可编辑文本”
可降级性关闭后端服务后，记录创建、录音、编辑、导出仍可正常使用
数据安全前端产物与仓库中不存在任何 API 密钥；删除记录后音频与文本一并清除
内容可信AI 初稿不新增原始转写中不存在的人物、时间、地点、事件
可用性所有可点击控件有效区域不小于 48px，正文字号不小于 16px，状态均有文字提示

3. 目标用户与主要使用场景

3.1 用户角色

角色说明优先级
主要用户习惯口述表达、不熟悉电脑操作的中老年口述记录者P0
协助用户帮助父母完成麦克风授权、录音确认与文字校对的子女或照护者P0
非主要用户专业传记编辑、机构采集人员、多人家庭协作者不针对其设计功能

3.2 主要使用场景

场景一：老人独自在家录制人生经历

老人打开页面，新建一条“我的童年”，点击开始录音并讲述，结束后播放确认，交给系统转写和整理，阅读后修改并导出文档。全程不需要大量打字。

场景二：子女协助老人首次使用

子女陪在旁，协助完成麦克风授权、新建记录和录音确认；老人负责讲述与核对事实，子女协助修改文字，最后共同导出。

场景三：分多次记录同一主题

老人新建“我的一生”，先录童年，隔天再录工作经历，之后补录家庭生活。系统按录入顺序保留多段素材，并支持合并进同一份传记正文。

3.3 用户能力假设与设计约束

  • 能理解中文文字提示，能完成“点击一个明显的大按钮”这一级别操作。
  • 不假设用户理解“麦克风权限”“浏览器设置”“存储配额”等概念，相关提示必须使用日常语言。
  • 不假设用户会主动保存，因此保存动作必须显式、有文字反馈、并在离开前拦截未保存内容。
  • 不假设网络始终可用，因此离线时核心功能必须可用。

5. 开发命名与目录规范

本节为统一开发规范，用于固定工程目录结构、文件与代码命名、接口与环境变量的命名方式，确保前后端协作一致、便于后续维护与交接。

5.1 工程目录结构

项目采用前后端分离的单体结构，前端与后端各自独立，通过本机回环地址交互。web/ 为前端工程，server/ 为后端 Minimal API 工程，docs/ 存放方案与设计文档。

层级目录 / 文件说明
根目录web/　server/　docs/　README.md　.gitignore前端工程、后端工程、文档、说明与忽略规则
前端 web/src/　public/　index.html　package.json　vite.config.ts　tsconfig.jsonVite + Vue 3 标准结构，构建配置集中在根
前端 web/src/views/　components/　stores/　services/　db/　types/　utils/　router/　styles/按职责分目录，禁止跨层直接调用
后端 server/Endpoints/　Services/　Models/　Program.cs　appsettings.json　appsettings.Example.json端点、服务、模型分层，配置文件只提交示例
文档 docs/prd/　tech/　risk/需求、技术方案、风险预案归档

5.2 目录职责约定

  • views/：页面级组件，对应 P1–P6 页面，只负责布局与交互编排，不写数据存取细节。
  • components/：可复用展示组件，如录音按钮、状态提示、确认弹窗，不含业务状态。
  • stores/：Pinia 状态模块，按域拆分，如 storyStore、recorderStore、transcriptionStore。
  • services/：后端接口与外部能力封装，统一处理请求、超时与错误码。
  • db/：本地数据层，封装 IndexedDB 的读写，屏蔽底层细节。
  • types/：TypeScript 类型定义，Story、Segment、接口出入参等。
  • utils/：无业务依赖的纯函数，如时间格式化、音频指纹、校验规则。

5.5 数据字段与接口命名

  • 数据字段统一使用小写下划线：story_id、segment_count、transcribed_text，与数据结构表保持一致。
  • 接口路径统一使用小写复数名词，动词用 HTTP 方法表达：/api/transcriptions、/api/polish、/api/exports、/api/health。
  • 用户自定义的标识（记录标题、片段序号）不参与字段命名，仅作为数据显示。

5.6 环境变量与配置命名

  • 后端敏感配置使用全大写下划线，通过环境变量注入：ASR_API_KEY、ASR_ENDPOINT、AI_API_KEY、AI_MODEL。
  • 公开可提交的配置使用示例模板：appsettings.Example.json，真实值写入未入库的 appsettings.Local.json。
  • 前端仅使用构建期公开变量，前缀 VITE_，且不得放入任何密钥：如 VITE_API_BASE。
  • .gitignore 必须忽略：本地配置、node_modules/、dist/、bin/、obj/、日志与临时文件。

5.7 Git 提交规范

  • 提交信息使用 类型: 简述 格式，类型取 feat / fix / docs / refactor / chore。
  • 一次提交只做一件事，便于回溯与回退；里程碑节点打 tag，如 m1-local-record。

6. 非功能需求

6.1 性能

指标目标值说明
首屏可交互时间本地环境 ≤ 2 秒不含外部服务
录音按钮响应≤ 100 毫秒点击到出现状态文字
列表渲染100 条记录内无卡顿超出后分页或虚拟列表
单段音频上限30 分钟超出时提示分段
转写状态刷新≤ 1 秒轮询或服务端推送
导出生成≤ 5 秒单篇传记，正常长度

6.2 安全

  • 外部服务密钥只存在于后端环境变量，前端产物、仓库、日志中不得出现。
  • 后端仅监听回环地址，不对局域网或公网开放；跨域只允许本地前端源。
  • 上传接口限制文件类型、单文件大小与请求频率，拒绝超限请求并返回明确提示。
  • 所有外部输入（标题、正文、文件名）做长度限制与内容转义，避免注入。
  • 删除记录时同步清理音频、原始转写文本与润色文本，不留孤儿数据。

6.3 隐私与数据合规

  • 页面必须明确说明：记录默认保存在当前设备和当前浏览器，不提供跨设备同步。
  • 调用外部语音识别或 AI 服务前，以文字提示用户音频或文本将被上传处理，需用户确认后继续。
  • 后端处理请求时不将音频落盘，仅做透传与返回。
  • 提供“清除全部本地数据”入口，并说明后果。
  • 传记内容默认不公开、不分享、不上传任何第三方展示平台。

6.4 兼容性

环境支持级别说明
Chrome / Edge 最新两个大版本完全支持主要验证环境，支持录音与本地存储
Safari基础支持录音格式差异需转换，转写功能可用但需验证
Firefox基础支持录音可用，不作为主验证环境
移动端浏览器不承诺界面按最小宽度 768px 设计
后端运行时.NET 运行时与课程项目既有技术栈一致

6.5 可用性与无障碍

  • 按钮有效点击区域不小于 48px，正文与提示字号不小于 16px。
  • 每页只设置一个主要操作按钮，次级操作视觉权重明显更低。
  • 所有状态（录音中、转写中、保存中、失败）必须有文字说明，不能只用颜色或动画表达。
  • 错误提示需给出下一步动作，例如“请允许使用麦克风后重试”。
  • 危险操作（重新录制、删除记录、放弃未保存内容）必须二次确认。

6.6 可维护性与可测试性

  • 前端使用 TypeScript，业务逻辑与界面组件分离。
  • 数据读写、状态流转、导出组装等核心逻辑需可单元测试。
  • 后端接口保持无状态与幂等设计，便于重复调用与问题复现。
  • 关键流程具备可观测的日志等级划分，但日志不得记录音频内容与正文原文。

6.7 成本约束

  • 语音识别与 AI 调用按次计费，需设置单次时长上限、单日调用上限与失败重试上限。
  • 相同音频重复转写应命中本地缓存，避免重复计费。
  • 优先使用本地能力（浏览器录音、本地存储、本地编辑）降低服务成本。

7. 关键流程与技术约束

7.1 端到端主流程

新建记录 → 录音（可多段）→ 语音转文字 → AI 润色生成初稿 → 在线编辑 → 导出 DOCX

该流程为单向主路径，任何一步失败都必须保留前序成果，并允许用户重试当前步骤而不是回到起点。

7.2 录音流程

  1. 进入录音页，展示当前记录标题与已录片段数量。
  2. 点击“开始录音”，浏览器请求麦克风权限；被拒绝时提示重新授权方法。
  3. 录音中显示“正在录音”与已录时长，可暂停与继续。
  4. 点击“结束录音”，生成本地音频对象，显示时长。
  5. 用户可播放试听，选择“重新录制”或“确认录音”。
  6. 确认后写入本地存储，生成片段序号与状态。

7.3 转写与润色流程

  1. 用户点击“开始转写”，前端将音频发送至后端转写接口。
  2. 后端调用外部语音识别服务，返回原始转写文本，前端仅新增该字段。
  3. 转写结果为空或异常时提示重录或更换音频，原音频保留。
  4. 用户点击“生成传记初稿”，前端提交原始转写文本（汇总全部已转写片段）。
  5. 后端按固定提示词约束调用 AI，返回润色文本。
  6. 页面分区展示“原始转写文本”和“AI 润色文本”，并提示核对事实。

技术约束：原始转写文本与润色文本必须分字段存储，润色结果不得写回原始转写字段；AI 返回内容不得新增原始文本中不存在的人物、时间、地点与事件。

7.4 多段口述合并流程

  1. 同一记录下按录入顺序保存多个片段，序号稳定不变。
  2. 合并时按序号拼接各片段转写文本，片段之间以分隔标记区分。
  3. 提示词要求 AI 保持时间顺序与事实一致，不得改变片段之间的逻辑关系。
  4. 用户可删除单个片段；删除后序号重排并提示重新生成初稿。

7.5 编辑与保存流程

  1. 进入编辑页展示标题与润色正文。
  2. 用户修改后点击“保存内容”，写入本地存储并更新时间。
  3. 保存成功显示“内容已保存”，失败显示“保存失败，请稍后重试”。
  4. 存在未保存改动时离开页面，弹出确认并在用户确认后丢弃。

7.6 导出流程

  1. 点击“导出文档”，先校验标题是否为空、正文是否为空、是否存在未保存修改。
  2. 校验失败时提示用户先补齐或先保存，不进入生成环节。
  3. 通过后由后端组装 DOCX（标题、正文、创建时间、基本段落结构）。
  4. 浏览器触发下载，页面提示“文档已导出，请在下载目录中查看”。

7.7 删除流程

  1. 在记录列表或详情页选择删除。
  2. 弹出二次确认，明确说明将同时删除音频、原始转写与润色文本。
  3. 确认后清除本地数据并刷新列表，显示“记录已删除”。

7.8 异常与恢复原则

异常处理原则
麦克风未授权文字提示重新授权方法，保留当前页面状态
录音中断或失败保留已录部分或提示重新录制，不静默丢弃
转写失败保留音频与已有文本，提供重新转写入口
转写结果为空提示环境嘈杂或音频过短，建议重录
AI 生成失败原始转写文本不丢失，可稍后重试
网络中断页面状态保留，提示联网后重试；本地功能继续可用
本地存储不足提示清理或导出后删除旧记录
导出失败编辑结果保留，允许再次导出

8. 技术方案

8.1 总体架构

层组成职责
界面层Vue 3 单页应用页面结构、交互、状态展示与文字反馈
状态与业务层Pinia Store + 领域服务模块记录与片段状态、流程编排、校验规则
本地数据层IndexedDB（音频以 Blob 存储）记录、片段、文本的持久化与读取
接口层后端 HTTP 接口（本机回环地址）转写、润色、导出，均为无状态处理
外部服务层语音识别服务、AI 服务仅由后端调用，密钥保存在后端

数据流向：界面层读写本地数据层完成核心业务；只有转写、润色、导出三类操作经由接口层访问后端，后端不持久化用户数据。

8.2 技术栈选型

类别选型理由
前端框架Vue 3 + TypeScript组件化清晰，类型约束降低维护成本
构建工具Vite启动与构建速度快，配置简单
状态管理Pinia与 Vue 3 官方配套，状态流转易测试
路由Vue Router页面路径与离开拦截能力
样式方案Tailwind CSS统一间距与字号体系，便于落实可访问性尺寸要求
本地数据库IndexedDB（通过轻量封装库访问）可存储音频二进制与长文本，容量优于 localStorage
录音浏览器 MediaRecorder零额外依赖，符合“语音优先”录入要求
后端ASP.NET Core Minimal API与既有课程项目技术栈一致，便于复用经验
文档导出后端生成 OOXML（DOCX）无需安装 Office 组件，产物可靠且可编辑

8.3 关键决策与取舍

决策一：数据保存位置

采用本地优先方案：记录、音频、文本全部保存在浏览器 IndexedDB，后端不持久化用户数据。

理由：与“不提供云同步”的产品边界一致；隐私风险最低；后端故障不影响核心功能；后续若增加云同步，仅需在本地数据层之上增加同步适配，不必重写业务逻辑。

代价：清理浏览器数据会丢失记录，因此必须提供导出能力与明确提示，并在删除前二次确认。

决策二：语音识别与 AI 调用方式

统一经由自有后端代理调用，前端不直接请求第三方服务，也不内置任何密钥。

备选方案：使用浏览器内置语音识别接口，可省去后端与费用，但长音频稳定性差、依赖特定浏览器、且会将音频交给浏览器厂商，不作为第一版主路径，仅作为无后端时的可选降级。

决策三：DOCX 导出实现

由后端组装 OOXML 并直接生成 DOCX，不依赖 Office 组件与第三方重量级库。

理由：该方式已在同类课程项目中验证可行；产物可被 Word 与 WPS 正常打开；生成逻辑纯函数化，易测试。

决策四：多段口述的数据形态

把单表设计拆分为“记录 + 片段”两级结构，解决多段录音无法用单一音频字段表达的问题。

8.4 数据结构设计

记录（Story）

字段类型说明
story_id字符串唯一标识，创建时生成
title字符串记录或传记标题
polished_text长文本AI 润色后的传记正文，可被用户编辑覆盖
status枚举未录入 / 转写中 / 待编辑 / 已完成
segment_count整数片段数量，用于列表展示
created_at日期时间首次创建时间
updated_at日期时间最近修改时间
last_saved_at日期时间最近一次保存正文或标题的时间

片段（Segment）

字段类型说明
segment_id字符串片段唯一标识
story_id字符串所属记录标识
order_index整数录入顺序，用于排列与合并
audio_blob二进制音频数据，保存在本地数据库

audio_status枚举未录音 / 录音完成 / 已确认 / 录音失败

transcription_status枚举未开始 / 处理中 / 成功 / 失败

数据处理原则

  1. 原始转写文本与润色文本分字段保存，禁止相互覆盖。
  2. 用户编辑结果以润色字段为准，原始转写文本仅作参照。
  3. 第一版不做历史版本，更新时间只表示最近一次修改。
  4. 删除记录时级联删除其全部片段与音频。

8.5 接口清单

方法路径说明阶段
GET/api/health服务健康检查，用于前端判断智能能力是否可用M1
POST/api/transcriptions提交音频，返回原始转写文本M3
POST/api/polish提交原始转写文本，返回润色正文M3
POST/api/exports提交标题与正文，返回 DOCX 文件M2

记录与片段的增删改查全部在本地完成，不经过后端接口，因此接口层保持极小且无状态。

约束：接口必须对同一输入保持幂等；转写与润色接口需设置超时与重试上限，超时后返回可识别的错误码，前端据此提示用户重试。

8.6 存储与配额策略

  • 音频以二进制形式存储，30 分钟音频量级较大，需在录音结束前预估剩余配额。
  • 剩余空间不足时阻止继续录音，并提示导出后删除旧记录。
  • 转写结果按音频指纹缓存，避免重复调用产生费用。
  • 不保存临时中间文件；导出完成后不保留服务端副本。

8.7 环境与配置

  • 后端密钥通过环境变量注入，本地开发使用未入库的本地配置。
  • 仓库中只提交示例配置模板，不含任何真实值。
  • 前端通过构建期变量区分本地与部署环境，构建产物中不得出现密钥。

9. 页面结构与原型规划

9.1 信息架构

编号页面主要操作优先级
P1首页 / 记录列表新建口述记录P0
P2新建记录开始录音P0
P3录音页开始录音 / 确认录音P0
P4转写与初稿页开始转写 / 生成初稿P0
P5在线编辑页保存内容P0
P6导出确认导出文档P0

9.2 P1 首页 / 记录列表

顶部为页面标题；中部为记录列表，每条显示标题、更新时间和当前状态；底部为唯一主要按钮“新建口述记录”。列表为空时显示“还没有口述记录，可以先创建一条记录”。每条记录提供继续编辑、查看与删除三个次级入口，删除需二次确认。

9.3 P2 新建记录

仅包含一个标题输入框与一个主要按钮“开始录音”。标题为空时点击按钮提示“请先填写记录标题”。创建成功后提示“记录已创建，接下来可以开始录音”，并进入录音页。

9.4 P3 录音页

页面顶部显示当前记录标题与已录片段数量。主要按钮为“开始录音”，次级操作为暂停、继续、结束、播放、重新录制、确认录音。录音中必须显示“正在录音”与实时时长。备用入口“上传音频”视觉权重低于录音按钮。未确认音频前不得自动进入转写。

9.5 P4 转写与初稿页

分区展示转写进度、原始转写文本和 AI 润色文本，两区标题明确区分。页面固定显示提示“AI 生成内容可能存在错误，请核对人物、时间、地点和事件”。主要按钮根据阶段切换为“开始转写”“生成传记初稿”“进入编辑”。失败时展示原因与重试入口。

9.6 P5 在线编辑页

上方为标题输入框，下方为普通文本编辑区，不提供任何富文本工具栏。主要按钮为“保存内容”。存在未保存改动时离开页面，弹出“当前内容尚未保存，是否保存后离开？”，提供保存并离开与放弃修改两个选项。

9.7 P6 导出确认

以弹窗或独立区块呈现，展示将要导出的标题与正文摘要。主要按钮为“导出文档”。校验失败时给出对应提示：标题为空、正文为空、存在未保存修改。导出中显示“正在生成文档，请稍候”，完成后显示“文档已导出，请在下载目录中查看”。

9.8 统一交互与视觉规范

  • 每页仅一个主要按钮，次级操作视觉权重明显更低。
  • 所有可点击区域不小于 48px，正文与提示字号不小于 16px。
  • 状态变化必须伴随文字提示，不使用仅颜色或仅动画的表达。
  • 错误信息遵循“原因 + 下一步动作”的固定句式。
  • 危险操作统一采用二次确认弹窗。
  • 页面主色与间距保持统一，避免同一层级出现不同视觉规格。

11.3 专项风险降级方案

针对本项目的三类核心风险，明确具体的降级路径，保证任一能力失效时产品仍可继续使用。

风险一：用户口述隐私信息保护

  • 数据默认只保存在当前设备浏览器（IndexedDB），不提供跨设备同步，从源头降低集中泄露风险。
  • 仅转写、润色、导出三类操作会离开本机，且发送前必须以文字提示用户，确认后才允许发送。
  • 后端只做透传，不将音频落盘、不写入数据库；日志仅记录调用次数与耗时，禁止记录音频内容与正文原文。
  • 提供“清除全部本地数据”入口，删除记录时级联清除音频、原始转写文本与润色文本。

风险二：语音文件存储异常

  • 录音结束先校验音频非空与时长有效，通过后才写入本地数据库；写入失败时保留内存副本并提示重录，不静默丢弃。
  • 存储配额不足时提前阻止继续录音，提示用户导出或删除旧记录后再录。
  • 音频上传前校验格式与单文件大小，不支持的格式直接给出可理解的提示；上传中断时保留原始音频并允许重试。
  • 转写成功前不删除原始音频，保证转写失败时可重新提交。

风险三：AI 生成内容失真（幻觉）

  • 提示词固定约束：只允许在原始转写文本范围内整理语言，禁止新增任何人物、时间、地点与事件。
  • 原始转写文本与润色文本分字段存储、分栏展示，润色结果不得写回或覆盖原文。
  • 页面固定展示“AI 生成内容可能存在错误，请核对人物、时间、地点和事件”的提示。
  • 导出前提示用户已完成核对；AI 不可用时整条链路降级为“人工编辑 + 导出”，不影响交付。

12. 验收标准

12.1 功能验收

  1. 可新建记录、修改标题、查看列表、删除记录，且删除前有二次确认。
  2. 可完成一次或多次录音，显示时长，可暂停、继续、结束、播放与重新录制。
  3. 刷新或重新打开页面后，记录与音频仍然存在。
  4. 可对音频执行转写，得到原始转写文本，且原文不被润色结果覆盖。
  5. 可生成 AI 传记初稿，可对多段口述合并生成。
  6. 可编辑标题与正文并保存，离开页面前有未保存提示。
  7. 可导出包含标题与正文的 DOCX，且文件能被正常打开。
  8. 上述任一环节失败时，已有内容不被覆盖或丢失，并提供重试入口。

12.2 技术验收

  • 后端接口对同一输入返回稳定结果，超时与失败有明确错误码。
  • 关闭后端服务后，记录创建、录音、编辑、导出之外的本地功能仍可用。
  • 本地存储读写失败时给出可理解提示，不出现界面无响应。
  • 核心逻辑具备单元测试，覆盖状态流转与数据组装。

12.3 安全与隐私验收

  • 前端构建产物、仓库文件、日志中均不存在任何密钥或凭据。
  • 后端仅监听回环地址，非本地来源请求被拒绝。
  • 调用外部服务前有明确文字提示，用户确认后才发送数据。
  • 删除记录后，音频与文本均被清除，无残留数据。

12.4 演示验收脚本

  1. 打开首页，新建记录“我的一生”。
  2. 录制第一段童年经历，播放确认后录入成功。
  3. 追加第二段工作经历，展示多段顺序。
  4. 执行转写，展示原始转写文本。
  5. 生成传记初稿，展示与原文的区分与事实提示。
  6. 修改标题与正文并保存，刷新页面确认内容仍在。
  7. 导出 DOCX 并当场打开，确认标题与正文正确。
  8. 演示一次失败场景（例如断开后端后转写），确认内容未丢失且有重试入口。
